# UV-5RH Pro V2：FD6818 调谐字、RFIC RX/TX 状态与键盘 UI 控制流

更新：2026-11-17。此次分析以原厂 `BF_5RH_501_v2_0_9.dat` Thumb 机器码为主，交叉核对 V1.1.04 中已独立定位的 FD6818 两线寄存器接口，另参考 [FD6818 REV.1.0.0 Programming Guide（机器译文）](https://www.glaver.org/blog/UV-17/FD6818.pdf) 第 18–20 页。目的在于继续推进**可验证的独立固件核心**，不把未测量的 QFN 引脚、RF 输出和完整板级驱动当成事实。

## 1. 已确认的 V2.0.09 频率写入路径

| 阶段 | 原厂地址/指令 | 直接结论 |
| --- | --- | --- |
| 运行态原始调谐表查询 | `0x0800DDB8` → `0x0800DDC4 LDR.W R0,[R1,R0,LSL #2]` | 根据 SRAM 索引从 `0x2000246C` 中取出 32 位原始调谐字 |
| 修正量相加 | `0x0800AFE4` → `0x0800AFEC BL 0x0800DDB8` → `0x0800AFF0 ADD R0,R4` | 使用 ARM 32-bit 加法，结果可能溢出回绕；修正参数从函数输入到达 |
| 写入 RFIC | `0x0800AFF2 BL 0x08005EC6` | 调用 RFIC 32 位调谐写入函数 |
| 高频半字 | `0x08005ECA–0x08005ECE` | 寄存器 `0x39` 接收 `word[31:16]` |
| 低频半字 | `0x08005ED2–0x08005EDA` | 寄存器 `0x38` 接收 `word[15:0]` |

因此，**已经闭合的是“SRAM 表 + 原始修正字 → FD6818 寄存器”的整段软件数据流**。尚未找到这张 SRAM 表的完整填充与射频校准生成算法。不能直接断言每条业务频率都没有本机的补偿量，也不能把 SRAM 的 raw word 当作用户界面 Hz 值。

### 1.1 10 Hz 算法有了独立 FD6818 资料支撑

FD6818 REV.1.0.0 编程指南的频率设置章节（印刷第 20 页）给出：

```text
raw = (REG_39H << 16) | REG_38H
frequency_hz = raw * 10
```

指南示例：409.75 MHz → `0x02713A98`，分别写 `0x39 = 0x0271`、`0x38 = 0x3A98`。该关系与 V2 本机原厂的 `0x39/0x38` 写入布局一致，已实现于 `firmware-pro/core/src/fd6818.rs` 的 `frequency_hz_to_word`、`write_frequency_hz`。输入 Hz 到 10 Hz 的舍入由核心定义；不限制使用频段，只限制 32 位表达能力。

**证据分级：** FD6818 标准编码公式属于编程手册直接证据；UV-5RH Pro 使用相同寄存器半字布局属于原厂机器码直接证据；“全部本机调谐结果完全等于 Hz/10、无需校准”仍未由运行期表与实测闭合。因此 `write_oem_corrected_tuning_word` 继续支持原始 32 位修正量，并未被 Hz 接口替代。

## 2. 从原厂 RF 状态字恢复芯片级接收/发射指令

原厂 V2 `0x0800B070 MOVW R1,#0xC1FE`、`0x0800B0A0 MOVW R1,#0xBFF1` 分别进入寄存器 `0x30` 写入路径。编程指南印刷第 18 页将 `0xBFF1` 列为 RXON、`0xC1FE` 列为 TXON，并要求状态变化先写 IDLE=0。

| RFIC 操作 | 直接写入值 | 原厂事实与实现状态 |
| --- | --- | --- |
| 芯片空闲 | `0x30 ← 0x0000` | 本机原厂可见；独立核心提供 `RficState::Idle` |
| 芯片接收 | `0x30 ← 0x0000`、随后 `0x30 ← 0xBFF1` | 与原厂 V2 常量和手册 RXON 相互吻合 |
| 芯片发射态 | `0x30 ← 0x0000`、随后 `0x30 ← 0xC1FE` | 与原厂 V2 常量和手册 TXON 相互吻合 |

**寄存器编号差异：** 编程指南将该状态字写在 `0x03`，而本机 V2 实际原厂向 `0x30` 写值。这可能属于厂商寄存器映射/修订差异，不能靠“常见 FD6818 实现”直接改写成本机 `0x03`。我们独立核心的 `select_rfic_state` 严格以 OEM `0x30` 为准。

**物理 TX 不等于 RFIC TXON。** GPIO PA 偏置、天线切换、PTT 输入、声音收发路径、不同频段校准和 PLL/VCO 的完整状态机都未封闭。独立核心暴露芯片级 RX/TX 状态指令，不把它写成“整机已经能正确发射”。

## 3. 原厂频率配置序列：一个已验证的 RFIC 前缀

函数 `0x0800A428` 在参数中接收一个 **raw 32-bit** 频率值。它执行的可验证前缀：

```text
0x51 <- 0x0300
0x39 <- raw[31:16]
0x38 <- raw[15:0]
0x37 <- (cache_37 & 0xFDF0) | 0x020F
0x30 <- 0x0000
0x30 <- 0xBFF1
delay_helper(0x0190)
```

`0x0190` 是原厂延时子程序的**原始参数**，在没有完整时间基准之前不得擅自解读为 ms、CPU 周期或特定固定秒数。

独立 Rust `no_std` 驱动提供 `apply_oem_setup_prefix`，通过 `StockDelay` trait 把延时交由未来板级 HAL 实现。每一步均保留可传播的 I2C 错误并在 Host 模拟总线上检查顺序。这只是已核实的**前缀**，不能由此断言 `0x0800A428` 的后续状态、厂商校准和完整开机序列均已逆向。

## 4. UI 与键盘事件：已经找到消费路径，但真实键名仍未知

在先前完整 22 项扫描码表的基础上，V2 新增交叉证据如下：

- `0x08010AB6 BL 0x08010998`：主 UI 事件逻辑调用已有 GPIOC 两阶段键扫描。\n- `0x080109A2–0x080109AC`：键盘扫描器同时读取 GPIOA IDR 的 bit9，并将低电平识别为有效输入，写入 SRAM `0x2000009D` 标志；这一路不属于22项 GPIOC 矩阵码表。当前仍**不能认定它就是实际 PTT**，但已将其作为单独的 active-low HAL 输入加入 Rust 核心。
- `0x08010AD4` 与 `0x08010AD8`：事件条件分支检查逻辑键索引 `0x13`、`0x14`。
- `0x08010B46` 与 `0x08010B4A`：在另一段上下文重复判断相同逻辑索引。
- `0x0800B0D8`、`0x0800B0F0`：RF 辅助例程中也调用键扫描并与 `0x0D` 比较。

这些静态证据**能够定位软件如何消费键事件**，不能直接唯一确定实体键帽标签。特别是 `0x0D` 不能未经完整业务函数语义证明就标注为 PTT。原厂菜单页面布局、字库/图片映射、长按事件与背光控制仍需单独逆向。特别是 USART1 与 GPIOA bit9 存在潜在引脚复用/不同编译配置问题，不能仅由外设功能名称推断物理线缆。

## 5. 交付代码与测试口径

```sh
python tools/pro_v2_rf_ui_flow_audit.py --json
python -m unittest discover -s tests -v
cargo test --manifest-path firmware-pro/core/Cargo.toml --offline
cargo check --manifest-path firmware-pro/core/Cargo.toml --lib --offline
```

- `tools/pro_v2_rf_ui_flow_audit.py`：验证 V2 机器码指令点、PC 相对 literal、原厂直接 BL 调用，以及 V1 已验证的寄存器接口基础。
- `tests/test_pro_v2_rf_ui_flow_audit.py`：原始二进制正例、关键常量/跳转/指令变异负例和原始 32-bit 校正数学。
- `firmware-pro/core/src/fd6818.rs`：加入原厂确认的寄存器配置前缀、32 位修正调谐、指南匹配的 10 Hz 单位编码和芯片级 RX/TX/IDLE 状态，新增模拟 I2C/延时测试。

本次不会生成可刷的 `.dat`、`bin` 或号称实机通过的正式替代固件。**下一步仍须继续逆向实际板级 HAL 的 TX PA GPIO、模拟音频、按键物理标签、LCD 控制器初始化/背光，以及 MCU 真实型号和物理 Flash 映射。** 这些不属于可以凭软件宏名猜定的内容。
