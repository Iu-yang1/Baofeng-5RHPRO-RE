# XL9951Q：Reset 到恢复函数的静态可达性与 SPI NOR 错误传播审计

日期：2026-11-16。原厂 V1.1.04 / V2.0.09 固件离线审计。接续 [高地址 NOR 日志与恢复状态机报告](xl9951q-journal-cold-start-recovery.zh-CN.md)。

**结论：** 两版原厂应用的 Reset 向量、启动包装函数、scatterload 至 main 的静态路径和 main 调用恢复函数的指令链已经衔接并验证；NOR 字节传输有每次传输的计数超时，但返回值 `0x00` 同时代表“传输失败”和“合法收到全零状态”；NOR 的 WIP 轮询本身没有独立总超时，写入后的状态也没有向日志清除路径传递有效的错误信号。所有测试为原厂存档机器码的离线静态验证，不是物理断电、SPI 总线或 Bootloader 测试。

## 1. Reset → main → 恢复函数

| 验证项 | V1.1.04 | V2.0.09 |
| --- | --- | --- |
| 镜像内向量表 Reset 指针（`0x08001004`） | `0x0800123D` | `0x0800123D` |
| Cortex-M Thumb Reset 入口 | `0x0800123C` | `0x0800123C` |
| 启动时钟初始化包装函数 | `0x080262A8` | `0x080323DC` |
| ARM scatterload 交接函数 | `0x08001220` | `0x08001220` |
| 原厂 main 函数 | `0x08027BE8` | `0x080340E0` |
| main 中直接 `BL` 恢复函数 | `0x08027BFC` | `0x080340F4` |
| 恢复函数 | `0x0800AB74` | `0x08010400` |

本轮复用了已被原始固件字节测试验证的 `v2_pll_runtime_order.verify_reset_to_main`，并新增要求向量表 Reset 项**精确等于 `0x0800123D`**。main 起始到恢复调用点之间经线性指令窗口与函数内 CFG 两重检查，确认该代码窗口没有局部条件跳转，且直接 BL 目标正是已验证的恢复入口。早期 PLL/延时帮助函数若返回，main 将按源码顺序调用恢复函数。

**条件限定：** 这证明的是软件控制流路径和正常返回前提，不能证明 CPU 实际进入该向量表、未知 Bootloader 未改向量、每个早期调用都成功返回、真实时钟稳定，或者所有复位类型都一定执行恢复。

## 2. SPI 单字节交换确有超时

| 操作 | V1 指令 | V2 指令 | 事实 |
| --- | --- | --- | --- |
| 单字节 SPI3 交换 | `0x080257A0` | `0x08031814` | 两版同构 |
| TX 轮询计数与退出 | `0x080257AE/0x080257B0` | `0x08031822/0x08031824` | `CMP R4,#0xC8`，条件超限 |
| RX 轮询计数与退出 | `0x080257CE/0x080257D0` | `0x08031842/0x08031844` | `CMP R4,#0xC8`，条件超限 |
| TX/RX 任一超时出口 | `0x080257D2` | `0x08031846` | `MOVS R0,#0`，直接返回 |
| 正常接收出口 | `0x080257E8` | `0x0803185C` | `UXTB R0,R0`，返回接收字节 |

`0xC8` 是软件轮询计数阈值，不是 200 毫秒，也没有证据表明不同 CPU 主频下有固定时间含义。超时与合法字节 `0x00` 在返回 API 上没有可区分标志。

## 3. NOR 0x05/WIP 状态轮询没有独立总超时

| 逻辑 | V1 | V2 |
| --- | --- | --- |
| NOR WIP 等待入口 | `0x080030C8` | `0x08006BD8` |
| 发送 `0x05` | `0x080030D6` | `0x08006BE6` |
| 从 SPI 读取状态字节 | `0x080030DE` | `0x08006BEE` |
| 测试 WIP bit0 | `0x080030EA` | `0x08006BFA` |
| `WIP=1` 时向前循环 | `0x080030EC` | `0x08006BFC` |
| `WIP=0` 时返回 | `0x080030EE` | `0x08006BFE` |

在这两个完整的、边界已核实的函数中，只有状态 bit0 触发循环的条件跳转，没有独立计数器或 deadline。

由此有两种截然不同的故障模式：

- **设备持续报告 WIP=1：** WIP 轮询函数可能一直重试。如果看门狗、硬件复位或其他外部机制触发，则实际行为可被打断；它们不在本函数审计范围内。
- **SPI byte exchange 超时：** SPI 子函数返回 `0x00`，而 WIP 轮询对 bit0=0 视为完成。因此失败的读状态操作可能被当成“擦除/编程已完成”。

这里无需假设 NOR 芯片会返回异常数据；第二种歧义直接来自程序规定的 SPI 超时返回值。

## 4. 失败状态无法可靠传播到恢复日志清除

原厂页编程代码：

- V1 `0x08003182 BL 0x080030C8` 后直接 `0x08003186 CMP R6,R4`；
- V2 `0x08006C92 BL 0x08006BD8` 后直接 `0x08006C96 CMP R6,R4`。

这两个 CMP 比较的是剩余数据长度与当前编程块大小，而非状态轮询返回值 `R0`。页编程函数通过 `POP {...,PC}` 返回，在此范围内没有向上层提供独立的成功/失败状态。

外部 NOR 的扇区擦除函数在发送 `0x20` 后以无条件尾调用进入 WIP 轮询（V1 `0x08007CD6`，V2 `0x0800D376`）。恢复封装函数收到擦除函数返回后，直接启动整扇区页编程，不对擦除结果作错误判别。

最终：

- V1 `0x0800AC08` 执行备份恢复，紧接着 `0x0800AC0C` 擦除内部 Flash 事务日志；
- V2 `0x08010494` 执行备份恢复，紧接着 `0x08010498` 擦除内部 Flash 事务日志。

**可明确指出的故障模式：** 如果 SPI 读取的 WIP 状态因为传输超时而错误地返回 0，软件可在实际 NOR 操作未完成时继续后续操作，且恢复路径可能在没有确认扇区数据正确的情况下清除事务日志。该故障具备源代码级触发链和实际后果，但没有在实机上重复故障。

同一逻辑说明应把“发送了擦除/编程指令”“WIP 被认为已清除”“读回核对数据正确”视为三种不同的验收条件。当前恢复函数没有执行恢复之后的独立整扇区读回。

## 5. 与 MCU 内部 Flash 状态处理的区别

内部 Flash SR 读取函数位于 V1 `0x08002EAC` / V2 `0x080069BC`，会根据特定 SR 位区分若干返回码。它不能被外部 NOR 的 `0x05` WIP 轮询所替代。恢复末端的内部 Flash 日志擦除也未被独立成功检验。

因此不能把“内部 Flash 某处存在状态码返回”解释为整个 SPI NOR 恢复事务有完善的错误处理。
