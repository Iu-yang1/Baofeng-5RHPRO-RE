# UV-5RH Pro V2.0.09：时钟树、UART 与 TIM 函数级数据流逆向

日期：2026-11-15。对象：仓库 \`firmware/BF_5RH_501_v2_0_9.dat\`（原厂包，解包时剥离 \`0x50\` 头并 XOR \`0xC8\`），仅进行**离线反汇编**。用户设备固件 \`v2_0_09\`。

## 结论：可以重建“软件预期”的 48 MHz 时钟配置；不能将其当作实机频率测量

**默认寄存器复位状态、HEXT 就绪、PLL 切换完成、采用兼容位域和正确 SRAM 查表的条件下**：

\`\`\`text
                8 MHz（原厂程序编译时使用的 HEXT 数值）
                              |
                  PLL 输入 HEXT /1
                              |
                           PLL ×6
                              |
                         SYSCLK 48 MHz
                              |
                         AHB  /1
                              |
                          HCLK 48 MHz
                    +---------+----------+
                    |                    |
                 APB1 /2              APB2 /1
                    |                    |
                PCLK1 24 MHz         PCLK2 48 MHz
                    |                    |
              USART2 9600          USART1 115200
              USART3 19200         BRR16 ≈ 0x01A1
               BRR16=0x09C4
               BRR16=0x04E2
                    |
                TIM2/3/4 输入时钟 = 2 × PCLK1 = 48 MHz
                    |
            PSC = PCLK1 / 1,000,000 - 1 = 23
                    |
                 TIM 计数节拍 2 MHz
                    |
             ARR=1999 → 更新周期 1ms
\`\`\`

用户未进行实机晶振测量、SWD 寄存器读取或射频在环验证。**固件中直接观察到的是常量与指令，不是某个实际主频。**

### 验证结果

工作流：[V2 clock getter reconnaissance（见对应 PR / Actions）](https://github.com/Iu-yang1/Baofeng-5RHPRO-RE/actions/workflows/v2-clock-dataflow.yml)。工具 \`tools/v2_clock_tree_model.py\` 对真实镜像的寄存器掩码指令、常量池地址进行验证后才计算时钟配置；不直接套用预设 48 MHz。

## 1. Reset → ClockConfig → RCC_GetClocksFreq

V2 复位候选 \`0x0800123C\` 经 \`BLX\` 进入 \`0x080323DC\` 的 CRM 复位代码，再 \`BL 0x08031BF4\` 启动 HEXT/PLL。调用者 \`0x08032D18\` 通过 \`BL 0x08030C30\` 获取系统时钟频率表。

\`0x08030C30\` 的确切结构为：

| PC | 原始指令 / 数据 | 函数意义 |
| --- | --- | --- |
| \`0x08030C32\` | \`LDR R2, [PC,#0x90]\` → \`0x40021000\` | CRM/RCC 基址 |
| \`0x08030C36\` | \`0x007A1200\` = **8,000,000** | 内部/外部时钟的软件 8 MHz 常量 |
| \`0x08030C34–0x08030C44\` | \`CFG & 0xC\`，比较 \`0\`、\`4\`、\`8\` | SCLKSTS：内部时钟/外部时钟/PLL，只有选 PLL 时进行倍频计算 |
| \`0x08030C4E\` | \`CFG & 0x003C0000\` | PLL 倍频字段 bits21:18 |
| \`0x08030C58–0x08030C6A\` | 检查 **bit28**，按路径执行 \`((field|0x10)+1)\` 或 \`(field+2)\` | 扩展倍频解释；当 bit28=0、field=4 → **×6** |
| \`0x08030C54\` | \`CFG & 0x00010000\` | PLL 输入来源 |
| \`0x08030C6E–0x08030C7A\` | 检查 PLL 源及外部时钟预分频；加载 \`0x003D0900\` = **4,000,000** 或 8,000,000 | 在 HICK/2 或 HEXT/2 路径用 4 MHz，HEXT/1 时用 8 MHz |
| \`0x08030C7C–0x08030C7E\` | \`MUL\`、写 \`[R0]\` | 返回结构体偏移 0：SYSCLK |
| \`0x08030C80–0x08030C90\` | CFG bits7:4 查 \`0x20000018\` 起 SRAM 表、移位 | 偏移 +4：HCLK |
| \`0x08030C92–0x08030CA0\` | CFG bits10:8 查表、移位 | 偏移 +8：PCLK1 |
| \`0x08030CA2–0x08030CAC\` | CFG bits13:11 查表、移位 | 偏移 +12：PCLK2 |
| \`0x08030CAE–0x08030CC0\` | CFG bits15:14 经 SRAM 查表、\`UDIV\` | 偏移 +16：ADC 时钟 |

原始常量池：\`0x08030CC4 = 0x40021000\`，\`0x08030CC8 = 0x007A1200\`，\`0x08030CCC = 0x003D0900\`，\`0x08030CD0 = 0x20000018\`。

这些信息完整说明**原厂时钟查询函数的输入（CRM_CFG 与 SRAM 分频表）、选择分支、计算、返回结构体字段**。

注意：\`0x20000018\` 是**运行期 SRAM 表地址**。反汇编证明该函数从那里读取分频位移值，但目前没有独立证明该表的真实初始内容。工具中的 AHB/APB 分频位移表根据兼容标准定义建模；不能把它当作已经从实机 SRAM 读回的内容。

## 2. PLL 配置的原始位操作，及两种状态

按原厂 \`0x080323DC\`、\`0x08031BF4\` 两段指令依次操作 CFG：

\`\`\`c
// 数据流伪代码，仅供阅读，不是可直接刷机的 GPIO/时钟代码
cfg &= 0xF8FF0000;    // 0x080323EC，先保留部分高位
cfg &= ~0x007F0000;   // 0x08032402
cfg |= 0x00000400;    // 0x08031C50：APB1 /2
cfg &= ~0x003F0000;   // 0x08031C58：清 PLL 低位字段
cfg |= 0x00110000;    // 0x08031C60：HEXT 输入，倍频低位码 4
cfg &= ~0x00000003;   // 0x08031C76
cfg |= 0x00000002;    // 0x08031C7E：请求 SYSCLK 选择 PLL
\`\`\`

在 **CFG 原先为 0**、HEXT 8 MHz 的软件模型下：
- CFG 软件写入值模型：\`0x00110402\`（SWS 状态位由硬件更新，不包含在此写入值中）。
- PLLSRC=HEXT、外部时钟不预分频、倍频低位字段为 \`4\`，原厂查询函数计算 ×6；
- \`SYSCLK=48MHz\`；\`HCLK=48MHz\`；\`PCLK1=24MHz\`；\`PCLK2=48MHz\`。

**特殊保留条件：** 原厂启动清除位域时保留 CFG bit28；\`0x08030C58\` 查询函数却用它参与倍频计算。若这个位在进入代码前**已是 1**，固件的软件解释可以变为 \`(4|16)+1=21\`，即推得 \`8MHz ×21 =168MHz\`。这是工具单独报告的**条件分支示例**，并非 168 MHz 实机证据；它甚至可能因真实硬件位义不同而不是可用的时钟配置。

**厂商位定义重要差异：** [Artery AT32F403A/407 Reference Manual](https://doc.platan.ru/pdf/datasheets/artery/RM_AT32F403A_407_EN_V2_02.pdf) 把 PLL 倍频扩展定义在 **bits30:29**，bit28 则涉及 USB 分频；这与本固件 \`0x08030C58\` 的解释**不一致**。AT32F403A 不能因使用相似 CRM 基址就被认定为该固件的真实 MCU。另一方面 [ST RM0008](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101-stm32f102-stm32f103-stm32f105-and-stm32f107-advanced-armbased-32bit-mcus-stmicroelectronics.pdf) 的 STM32F1 PLL×6/APB1 /2、定时器 x2 语义与默认分支吻合，但它也不能唯一确认厂商。

## 3. USART 三个真实调用点与可算 BRR

全镜像 Thumb BL 调用点索引确认 \`USART_Init\` 风格函数位于 **\`0x08032CDC\`**，至少有以下三处直接调用；波特率是**原厂结构体中的实际常量**，没有假定：

| 调用 PC | 原厂结构体设置指令 | USART 基址候选 | 波特率 | 默认 48MHz 下 PCLK | 16 倍过采样 BRR 候选 |
| --- | --- | --- | ---: | ---: | --- |
| \`0x0800CA2A\` | \`0x0800CA08 MOV.W R0,#0x4B00\`，\`0x0800CA0C STR R0,[SP,#0x2C]\` | USART3 \`0x40004800\` | **19200** | 24MHz | **\`0x04E2\`** |
| \`0x08010306\` | \`0x080102E4 MOV.W R0,#0x2580\`，\`0x080102E8 STR R0,[SP,#0x2C]\` | USART2 \`0x40004400\` | **9600** | 24MHz | **\`0x09C4\`** |
| \`0x08018C20\` | \`0x08018BFE MOV.W R0,#0x1C200\`，\`0x08018C02 STR R0,[SP,#4]\` | USART1 \`0x40013800\` | **115200** | 48MHz | **\`0x01A1\`** |

以上 BRR 数值来源于 \`round(PCLK / baud)\`，仅适用于 STM32 兼容 USART 的 **16 倍过采样** 计算。原厂 \`0x08032D5E\` 还检查 CR1 bit15 并支持 **8 倍过采样**，因此在没有初始 CR1 状态/实机读数前，BRR 应写作预测值，不能声称实际寄存器已经是这些值。

**各 USART 与 GNSS、写频 K 口、调试或蓝牙的功能归属仍未知**；UART 端口配置证据不等于接线证据。

## 4. TIM 五个独立调用者的实际结构体/频率数据流

\`0x080324F8\` 的通用初始化程序从传入结构体偏移 \`+0\` 取得 PSC、\`+4\` 取得 ARR，并向 EGR 写入 1。五个独立调用者先以输出结构体接收 \`0x08030C30\` 的时钟信息，从 \`PCLK1\`（结构体 +8）计算：

\`\`\`c
uint16_t psc = PCLK1_Hz / 1000000 - 1;
TIMx->PSC = psc;
TIMx->ARR = caller_supplied_period;
TIMx->EGR = 1;
\`\`\`

已从 V2 实际指令读取的调用点：

| 时钟查询 BL | TIM 初始化 BL | 定时器候选 | ARR | 条件计数周期（48MHz 默认） | 更新周期 |
| --- | --- | --- | ---: | ---: | ---: |
| \`0x0800893C\` | \`0x08008966\` | TIM4 | **208** | 2 MHz | 104.5 μs |
| \`0x08009E98\` | \`0x08009EBE\` | TIM2 | **125** | 2 MHz | 63 μs |
| \`0x08012344\` | \`0x0801236E\` | TIM4 | **104** | 2 MHz | 52.5 μs |
| \`0x0801714E\` | \`0x08017174\` | TIM4 | **125** | 2 MHz | 63 μs |
| \`0x080193FC\` | \`0x08019426\` | TIM3 | **1999** | 2 MHz | **1000 μs（1 ms）** |

条件计算：APB1 /2 → \`PCLK1=24MHz\`；兼容 STM32F1 定时器规则 \`TIMxCLK=2×PCLK1=48MHz\`；\`PSC=24−1=23\`；\`f_counter=48MHz/(23+1)=2MHz\`。TIM3 的 \`ARR=1999\` 给出 1 kHz 更新频率。

**这个 1 ms 结果不能作为 48 MHz 主频的独立证明。** 若系统使用其他时钟（且 PCLK1 可整除 1MHz），调用者同步根据 PCLK1 调整 PSC，仍可能得到相同的 2MHz 计数节拍。它验证的是代码内部的频率和定时器倍频语义相容。

以上调用只说明静态代码路径，不能据此确认哪个定时器负责 APRS、音频、显示或硬件 PTT。

## 5. V1.1.04 / V2.0.09 代码复用，不能按固定差值映射全部函数

反汇编证实 V1 的 UART 初始化中 \`0x08026BE4\` **实际 BL 到 \`0x08024BBC\`**，而 V2 的 \`0x08032D18\` BL 到 \`0x08030C30\`。

离线逐字节验证：

| 函数或片段 | V1 地址 | V2 地址 | 两版对齐比较 |
| --- | --- | --- | --- |
| **时钟查询函数** | \`0x08024BBC\` | \`0x08030C30\` | **148/148 B 相同**，地址差 \`0xC074\` |
| USART 写 BRR 相邻代码 | \`0x08026C50\` | \`0x08032D84\` | **24/24 B 相同**，地址差 \`0xC134\` |
| TIM PSC/ARR 相邻代码 | \`0x0802640C\` | \`0x08032540\` | **24/24 B 相同**，地址差 \`0xC134\` |

如果错误使用 \`0xC134\` 去寻找时钟查询函数，只会找到 V1 的错误位置，并得到低相似度。此差异说明**仅函数级指纹确认后才可复用移植/重定位映射**。

相同的时钟查询函数代码只意味着 V1/V2 使用相同计算逻辑与常量；它们的实际 CRM 配置、外围电路和主频仍可能不同。

## 6. 反汇编、条件推导和待证实事项分别是什么

**原厂字节直接支持：** 8,000,000 / 4,000,000 两个数值、Reset 指令位操作、读 CRM_CFG 的条件分支、USART 配置 19200/9600/115200、五组 TIM ARR 与 PCLK1/1MHz 算法、V1/V2 148 B 与 24 B 对齐一致性。

**兼容语义推导：** HEXT 8MHz×6→SYSCLK48MHz；AHB/1、APB1/2、APB2/1；USART1/2/3 理论 BRR、APB1 TIMx2 与 1ms 定时器。

**尚未证实：** MCU 厂商与芯片料号、实物晶振 8MHz、PLL 扩展字段真实硬件语义及启动前原始值、SWS/PLL 就绪状态、SRAM 分频查找表内容、OVER8 的实际复位状态、UART 外设连接对象，以及设备在 RF 工作过程中的实时主频。

最值得继续的**纯软件**步骤是反汇编启动 RAM 初始化复制段，恢复 \`0x20000014\`/\`0x20000018\` 分频表实际初值，并沿 \`USARTx_TX/RX\` 函数与 GPIO AF 代码追踪哪个 UART 连接 ATGM336H-5N31。
