# XL9951Q 原厂应用：高地址日志与 SPI NOR 断电恢复控制流取证

日期：2026-11-16；分析对象：归档原厂 `BF_5RH_501_v1_1_04.dat`、`BF_5RH_501_v2_0_9.dat` 的解码后的 Thumb 程序。接续 [UpgradeTool IL / NOR 写入证据](xl9951q-upgradetool-il-spi-nor-journal.zh-CN.md)。

**范围与结论：** 已经在 V1、V2 中通过真实指令及直接 BL 调用验证了「开机初始化阶段检查 MCU Flash 日志元数据 → 对比 SPI NOR 备份与目标扇区 → 必要时擦除重写目标扇区 → 清除元数据」的恢复机制。存在恢复函数 **不等于** 已完成实机断电可靠性/事务原子性验收；没有获得 Bootloader，也没有连接电台、启动写频或烧录工具。

## 1. 入口及调用时序

| 目标 | V1.1.04 | V2.0.09 |
| --- | --- | --- |
| 早期初始化代码 | `0x08027BE8` | `0x080340E0` |
| 直接 `BL` 恢复函数 | `0x08027BFC` | `0x080340F4` |
| 恢复函数入口 | `0x0800AB74` | `0x08010400` |
| MCU Flash 8 字节读取 | `0x08007C80` | `0x0800D320` |
| NOR SPI 数据读取 | `0x0800E5CC` | `0x080141DC` |
| 不一致时擦除+写回 4096 B | `0x0800ED50` | `0x08014A28` |
| 内部 Flash 元数据擦除/清除入口 | `0x08007C68` | `0x0800D308` |

可观察的初始化顺序为：首先准备 `0x08000000` 常量并调用初始化函数，随后调用另一初始化函数和短延时；接下来通过上述 `BL` 执行恢复，再进入后续多个系统初始化调用。

这构成恢复函数在 **应用层早期初始化** 被引用的直接证据。后续已将归档镜像内 Reset 向量、startup/scatterload 到 main 的已验证指令路径与上述恢复 BL 连接，详见[Reset 可达性与 NOR 错误传播后续审计](xl9951q-reset-to-journal-nor-errors.zh-CN.md)。这是正常返回前提下的软件静态可达路径，仍不能声称所有实机启动、所有硬件故障条件下必然执行恢复。

此前 [高地址 NOR 审计脚本](../tools/xl9951q_high_flash_nor_audit.py) 中两个 `erase_journal` 标签分别写作 `0x08007C64` / `0x0800D304`，它们实际位于函数入口前的非本函数指令/填充半字。新的调用图确认入口是上表的 `0x08007C68` / `0x0800D308`，本轮已修正。

## 2. 高地址元数据的已证实格式

从 `0x0807F800` 读取 **8 字节**。分析记录如下：

| 内部 Flash 地址 | 内容 | 验证依据 |
| --- | --- | --- |
| `0x0807F800–0x0807F803` | 目标 NOR 扇区偏移（32 位**小端序**） | V1 `0x0800AB8E–0x0800ABA8`；V2 `0x0801041A–0x08010434` 按字节组合 `b0 + (b1<<8) + (b2<<16) + (b3<<24)`；应用写入路径使用两个 `STRH` 写入低、高半字 |
| `0x0807F804` | 事务完成标记，值 `0x01` 表示不需要恢复 | V1 `0x0800ABB0–0x0800ABB6`，V2 `0x0801043C–0x08010442`；写入端 V1 `0x08012E6C–0x08012E72` / V2 `0x080191B4–0x080191BA` |
| `0x0807F805–0x0807F807` | 本次恢复函数未解释的其余三个字节 | 仅确认这条路径读取了完整的 8 字节，不能据此声明全局未使用这些字节 |

空日志哨兵是目标偏移 `0xFFFFFFFF`，代码通过 `offset+1 == 0` 判断（V1 `0x0800ABAC`；V2 `0x08010438`）。这不同于完成标记 `0x01`，两者触发的分支不一样。

### 恢复决策表

| 目标偏移 | 第 5 字节 | 备份与目标比较 | 静态代码分支 |
| --- | --- | --- | --- |
| `0xFFFFFFFF` | 任意 | 不执行 | 跳过事务恢复，**此分支不执行日志清除** |
| 其他 | `0x01` | 不执行 | 直接执行日志清除 |
| 其他 | 非 `0x01` | 完全相等 | 不重复写目标，只清除日志 |
| 其他 | 非 `0x01` | 出现不一致 | 擦除目标 NOR 扇区、写回备份 4096 B，然后清除日志 |

决策表来自两版原厂指令；附带的纯 Python 分支模型仅做该逻辑的**离线场景枚举**，不是 MCU 仿真或实际故障注入结果。

## 3. 具体的 NOR 恢复控制流

两版恢复函数都会把备份读取位置设为 `0x001FE000`，长度设为 `0x1000`（4096 字节）。

- V1 `0x0800ABC0–0x0800ABC4`：备份进入 `0x20001CA8` 作为 SRAM 缓冲。
- V2 `0x0801044C–0x08010450`：备份进入 `0x20002580`。
- 比较过程以目标偏移为起始值，逐次加 `64` 字节读取目标 NOR 的区块，最多 `64` 个区块（共 4096 B），按字节与缓冲区数据对照。
- 仅在比较不一致时，V1 `BL 0x0800ED50` / V2 `BL 0x08014A28`。这两个函数都会先通过外部 NOR 的 `0x20` 扇区擦除路径，再把 `0x1000` 长度的缓冲区交给 `0x02` Page Program 链。
- 两版均在此之后无条件调用 MCU Flash 日志清除入口（V1 `0x0800AC0C`；V2 `0x08010498`），与恢复函数是否实际验证写回成功是两个不同问题。

由于 `0x001FE000` 位于 16 Mbit（2 MiB）存储器的倒数第二个 4 KiB 扇区，且该应用发送 `0x03` / `0x02` / `0x20` / `0x05` / `0x06` SPI 指令，原厂 [GT25Q16A 数据手册](https://www.giantec-semi.com/uploads/pdf/250709/GT25Q16A%20U%20DS_V2.2.pdf) 可用于解释这条软件协议。**但只能说明高度相容，不能用离线源码证明物理连接、器件厂商或 XIP 地址映射。**

## 4. 更新操作与意外断电的状态机

这是从原厂写入顺序与恢复分支共同构建的**逻辑状态模型**，并非实际断电测试。

| 阶段 | 写入路径动作 | 中断后重启时的理论行为 | 证据边界 |
| --- | --- | --- | --- |
| S0 | 擦除 `0x0807F800` 所在内部 Flash 元数据区域 | 目标 NOR 尚未被此事务改写；空日志可能使恢复跳过 | 片内 Flash 真实页尺寸未知 |
| S1 | 读取目标 4 KiB → 擦除 `0x001FE000` → 写备份 | 尚未登记新事务偏移；此时目标未开始被改写 | 未测试 NOR 备份写入失败或掉电 |
| S2 | 将原目标扇区偏移写入 `0x0807F800`，完成标志仍非 1 | 下次启动可识别待处理事务 | 未证实元数据半字写入具有原子性 |
| S3 | 修改或重写目标 SPI NOR 扇区 | 启动阶段比较备份与目标，不一致则全扇区恢复 | 无 CRC、失败注入或实机读回证据 |
| S4 | 目标更新完成后写 `0x0807F804 = 1` | 启动后跳过备份恢复并擦除日志 | 未证实电源时序下的实际完成条件 |

上述顺序还解释了为什么「先写备份、再写 MCU Flash 元数据」有意义：设计意图很可能是在 NOR 目标修改前确立恢复源。**设计意图不能代替真实硬件可靠性验证。**

### 已识别的具体风险

1. **恢复后日志清理没有独立成功判断。** V1 的 `BL 0x0800ED50` 直接接 `BL 0x08007C68`；V2 的 `BL 0x08014A28` 直接接 `BL 0x0800D308`。如果 NOR 擦除或编程最终失败，恢复记录有被提前清除的风险。此故障模式在源码路径中有依据，但尚无实机重现。
2. **恢复备份未见端到端完整性校验。** 检查的是备份与目标是否相同，而不是备份本身是否仍正确。备份受损时可能错误回写。
3. **元数据地址损坏缺少明显的独立界限校验。** 恢复函数只先检查 `0xFFFFFFFF` 与完成字节；此路径没有证明损坏的扇区偏移一定会被范围检查拒绝。NOR 底层仅发送 24 位地址字节，这可能放大高位损坏的风险。需要额外审计通用库和保护机制，不能声称已经观测到越界擦写。
4. **重启行为尚未经电源故障注入。** 普通 CI 单测能证明对原始机器码的解析和判定模型一致，不能证明真实复位、SPI 写周期、Brownout 电压下的原子性。

## 5. 交付的可重放静态验证

```sh
python -m pip install 'capstone==5.0.6'
python tools/xl9951q_journal_recovery_audit.py --json
python -m unittest discover -s tests -v
```

审计器在 V1/V2 各验证 **38 处**具体 Thumb 指令及相关的原始 `BL` 调用点，检查 PC 相对文字池引用、空日志哨兵、完成标志、比较循环、擦写封装调用和完成标志写入。回归测试对两版原始程序作正例、修改关键指令/BL/Flash 常量的负例，并用纯分支模型覆盖空记录、已完成、目标一致及目标不一致的分支。

**尚未证实：** 实体硬件执行启动路径的完整可达性、Bootloader 实际分区、XL9951Q 晶圆厂和内部 Flash 物理页规格、GT25Q16A 实际物理连接及端到端断电恢复的可靠性。
