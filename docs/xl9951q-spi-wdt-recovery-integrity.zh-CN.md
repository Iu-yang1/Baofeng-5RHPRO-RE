# XL9951Q 原厂应用：SPI3 传输失败、IWDG 看门狗与 NOR 事务完整性最终审计

日期：2026-11-17。分析对象：仓库归档原厂 `BF_5RH_501_v1_1_04.dat` 和 `BF_5RH_501_v2_0_9.dat` 解码后的 Thumb 代码，接续 [NOR 事务状态机](xl9951q-journal-cold-start-recovery.zh-CN.md) 和 [Reset → 恢复可达性、WIP 轮询](xl9951q-reset-nor-error-propagation.zh-CN.md) 两轮验证。

**范围：** 仅对原厂镜像执行本地解码、静态反汇编、PC 相对常量、直接调用点校验及逻辑分支测试。没有连接实机、执行升级程序、写入固件、读取设备 ID 或模拟真实供电波形。

## 1. 主要结论

1. **两版 SPI3 字节交换函数逐字节一致**：V1 `0x080257A0`、V2 `0x08031814`。两版均引用兼容 SPI3 寄存器基址 `0x40003C00`，使用发送及接收两次状态轮询。各自的计数器比较立即数均为 `0xC8`（200）；超时路径返回数值 `0`，但真实读回 `0x00` 也会返回 `0`。
2. **SPI3 的超时结果没有形成 NOR 的错误结果**：NOR 的 `0x05` Read Status Register (RDSR) 使用同一个字节交换函数发送 `0x05` 和 `0xFF`；接着仅测试返回字节 bit0（WIP）。如果第二次 SPI 交换**因超时返回零**，NOR 轮询也会把它判断为 WIP=0，从而错误结束等待。这一可观察的软件错误传播机制不依赖物理故障能否重现。
3. **正常主入口调用链在 NOR 恢复之前启动 IWDG**：V1 `0x080130A6 BL 0x0800AB40`，V2 `0x080193EE BL 0x080103CC`。两个包装函数都执行 `0x5555` 解锁、预分频/重装写入、`0xAAAA` reload，并通过尾跳转把 `0xCCCC` 写至 `0x40003000`；这是一套与 STM32F1 风格 IWDG 相容的启动序列。
4. **NOR 状态忙等待本身没有喂狗调用**。两版固件中另外确实存在 `0xAAAA` 喂狗调用点，但这两个已定位调用点不在 NOR RDSR 忙等待例程内部。若 NOR 一直报告 WIP=1，看门狗复位是与代码相容的结果；**不能**从离线程序证明必定复位，更不能未经 LSI 实测换算超时秒数。
5. **恢复完成后的备份完整性缺口没有闭合**：启动恢复例程把 `0x001FE000` 的 4096 B 备份与 NOR 目标逐字节比较，不一致时调用擦写封装，再立刻擦除 `0x0807F800` 元数据。该局部调用链中没有独立的备份 CRC/认证、写后全扇区读回，也未基于恢复结果决定保留日志。

## 2. 两版直接指令证据

| 检查项 | V1.1.04 | V2.0.09 | 解释 |
| --- | --- | --- | --- |
| SPI 字节交换入口 | `0x080257A0` | `0x08031814` | 76 B 序列在两版一致 |
| SPI 基址 `0x40003C00` | `0x080257A6 LDR` | `0x0803181A LDR` | PC-relative 文字池解析 |
| 首个轮询计数比较 `0xC8` | `0x080257AE` | `0x08031822` | 用于等待发送可用 |
| 第二个计数比较 `0xC8` | `0x080257CE` | `0x08031842` | 用于等待接收可用 |
| 两种超时返回公用的零值路径 | `0x080257D2` | `0x08031846` | `MOVS R0,#0` |
| 成功数据返回 | `0x080257E4–0x080257EA` | `0x08031858–0x0803185E` | 读取数据寄存器、截成字节、返回 |
| NOR RDSR 读状态 | `0x080030D8`, `0x080030DE` | `0x08006BE8`, `0x08006BEE` | 两次调用 SPI 字节交换 |
| WIP bit0 及分支 | `0x080030EA–0x080030EC` | `0x08006BFA–0x08006BFC` | `LSLS R0,#31` / `BNE` 回环 |
| IWDG 兼容寄存器基址 | `0x0800387C` 等处 | `0x0800738C` 等处 | `0x40003000` |
| IWDG 配置包装函数 | `0x0800AB40` | `0x080103CC` | 写解锁/分频/重装/喂狗/启动 |
| 启动路径配置调用 | `0x080130A6` | `0x080193EE` | `MOVS R0,#1` 之后 |
| 另外一处喂狗调用 | `0x0800E07A` | `0x08013C36` | 非 NOR RDSR 函数内部 |

两版字节交换函数各找到 **26 处直接 BL 调用**，包含 NOR 读取、编程、擦除及状态读取等路径。IWDG reload 函数在两版归档固件中各有两处直接 BL 调用：一处为启动包装函数内、另一处为运行阶段代码。本次枚举仅包含直接 BL 解析，不排除隐藏 ROM、函数指针或固件范围之外的操作。

### 2.1 超时为什么可能被误判为“不忙”

两版字节交换函数都在发送/接收状态检查时使用有限计数器。如果超过限定轮询次数，直接执行 `MOVS R0,#0` 并返回。上层 NOR RDSR 则是：

```text
send(0x05)                # 返回值没有在 RDSR 调用处独立检查
result = send(0xFF)       # 收到状态字节或超时返回 0
if (result & 0x01) != 0:
    repeat RDSR           # WIP=1
else:
    exit RDSR             # WIP=0，或者发生返回 0 的 SPI 超时
```

这是对静态机器码的**解释性伪代码**，不是可编译的刷机或测试固件。即使读状态字节没有超时，`0x00` 本身也可能表示合法空闲；仅凭这一个返回值不能区分两者。只要上层没有独立错误通道，**与正常空闲相同的零值就是此链路的可观测性缺口**。

## 3. IWDG 真实调用关系与复位边界

| 条件 | IWDG 兼容寄存器写入 | 说明 |
| --- | --- | --- |
| 启动包装函数参数为 `1` | `PR ← 4`、`RLR ← 0x07FF` | V1 主初始化经 `0x080130A6`、V2 经 `0x080193EE` 选择此分支 |
| 包装函数参数为 `0` | `PR ← 6`、`RLR ← 0xFFFF` | 此模式另有直接调用点，例如 V1 `0x08006A80`、V2 `0x0800C110`；芯片实际 RLR 宽度未知 |
| 任一配置分支尾部 | `KR ← 0xAAAA`，随后 `KR ← 0xCCCC` | 与 IWDG reload/start 操作语义相容 |
| NOR 忙等待例程 | 仅 SPI 字节交换/状态位循环 | 未发现对 `KR` 的独立喂狗调用 |

从主入口到模式 1 的软件序列是：

- V1：`main 0x08027BE8` → `BL 0x080111F0` → `B.W 0x080130A0` → `BL 0x0800AB40` → 主入口中的 `BL 0x0800AB74`（日志恢复）；
- V2：`main 0x080340E0` → `BL 0x080173DC` → `B.W 0x080193E8` → `BL 0x080103CC` → 主入口中的 `BL 0x08010400`（日志恢复）。

这些路径依赖前置函数正常返回。写入 `0xCCCC` 构成“应用代码请求启动 IWDG”的直接证据，**不构成电源实际复位、内部 LSI 频率或 XL9951Q 复位时间的测量**。尤其不应按照其他 MCU 的 12 位/16 位重装寄存器规格直接推出 `0xFFFF` 的实际有效值。

## 4. 错误场景与恢复保护结论

| 故障输入 | 代码级路径 | 可能结果 | 最终判定 |
| --- | --- | --- | --- |
| SPI 发送/接收状态迟迟不满足 | SPI byte transfer 计数超过 `0xC8` | 交换函数返回 `0`，调用方无法区分超时和正常零字节 | **已证实软件分支** |
| RDSR 返回 SPI 超时零值 | NOR status 检查 `result & 1` | 错误退出 WIP 等待，后续可能清除事务日志 | **已证实控制流、未实机注入** |
| NOR 始终返回 WIP=1 | NOR RDSR 循环没有自身的超时/喂狗 | 在 IWDG 已启动条件下有复位可能；如果复位后事务仍待恢复，可能反复启动重试 | **条件性推论，未测复位时序** |
| `0x001FE000` 备份内容损坏 | 启动恢复比较备份与目标，不先验证备份本身完整性 | 可能向目标回写受损内容 | **局部恢复路径无独立校验** |
| NOR 写入结束但最终字节错误 | 仅等待 WIP=0，然后调用日志清理 | 事务记录可能被过早擦除，失去再次恢复依据 | **局部调用链缺少写后校验** |
| 看门狗在 NOR 擦除过程中触发复位 | 复位后重新进入启动恢复判断 | 可能再次执行同一扇区回滚；是否能够完成取决于备份内容及硬件恢复 | **非原子性保障，仅状态机推导** |

这不是对用户电台的现存故障判断，也不是建议通过实机故障注入测试。**仅从现有归档固件可以闭合以上应用层错误传播路径，却无法闭合物理掉电可靠性、Bootloader 映射、芯片制造商鉴定。**

## 5. 验证与后续边界

复现：

```sh
python -m pip install "capstone==5.0.6"
python tools/xl9951q_spi_wdt_integrity_audit.py --json
python -m unittest discover -s tests -v
```

审计器在 V1/V2 各检查 **49 个**原始 Thumb 指令/PC-relative literal 位置，调用已有两轮 Reset 和 NOR 日志审计，并验证原始版每版 26 处 SPI 字节交换直接调用、两处 IWDG reload 直接调用。测试包含修改 SPI 返回零路径、忙等待跳转、IWDG 启动密钥、配置调用、MMIO literal 和寄存器写入的负例，以及状态位分支的小型纯 Python 模型。所有结果只归档 JSON 元数据，不包含固件二进制副本。

**本阶段离线研究结论已闭合：** 底层交换超时有检测但没有独立错误码；RDSR 可能错误判空闲；IWDG 在正常启动链中配置启动，WIP 例程内不喂狗；4 KiB NOR 备份与恢复没有在这条局部路径完成独立端到端校验。将此列为原厂软件架构中的具体限制即可，不必借芯片身份未知而否定其现有功能。

**进一步唯一需要新增的证据类型：** 受控只读实机观测或公开厂家 ROM/Bootloader、XL9951Q 数据手册、SPI 实测日志。用户当前限定的完全离线分析并不具备这些输入，故不能宣称这些硬件问题已经解决。
