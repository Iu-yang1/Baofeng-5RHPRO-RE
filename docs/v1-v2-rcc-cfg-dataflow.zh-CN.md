# UV-5RH Pro V1/V2：RCC 跨基本块地址传播与间接调用审计

日期：2026-11-15。研究基线：原厂 V1.1.04 与 V2.0.09 更新包（完整性校验、XOR 解码后读取 Thumb 字节）。**本轮仅静态离线研究，未读取物理 UID、ROM 内容、MCU 寄存器，也未刷机或连接实机。**

## 结论摘要

上一轮 [ROM/RCC MMIO 有界扫描](v2-0-09-rom-cfgr-mmio-audit.zh-CN.md) 只从文字池 `LDR` 开始，直线传播至多 32 条指令，遇分支即停止；在 V1/V2 中各找到 30 个唯一写入地址/目标寄存器候选。本轮增加基于 Thumb 控制流图（CFG）的数据流分析，结果：

| 指标 | V1.1.04 | V2.0.09 |
| --- | ---: | ---: |
| RCC 字面基址候选加载点 | 26 | 26 |
| 匹配到的 MOVW/MOVT 配对种子（指定范围） | 0 | 0 |
| 先前直线扫描的唯一 RCC 写入候选 | 30 | 30 |
| 本轮 CFG 扫描的唯一 RCC 写入候选 | **43** | **43** |
| CFG 相比直线扫描新增候选 | **13** | **13** |
| 到达单次分析预算上限的种子 | 0 | 0 |

其中新增写入集中于 RCC 标准库、Reset 早期时钟初始化的**同源函数**。没有在本轮能够确认的候选路径内发现新的独立应用状态/收发模式调频功能。**这不是证明不存在运行期调频**：当前仍有间接调用、RAM 别名和未建模地址生成方式等限制。

## 二、新分析器的实现边界

[tools/v2_rcc_cfg_dataflow.py](../tools/v2_rcc_cfg_dataflow.py) 分成两种入口证据：

1. **候选根：** 从原厂镜像经 Thumb 指令验证的 `0x40021000/0x40021004/0x400210F0` 文字池加载点，以及同一寄存器、96 字节以内能够配对的 `MOVW`、`MOVT`（高 16 位 `0x4002`）组合；为探索 SRAM 中转，再向前补充同一局部区域 32 字节以内的 `MOVW` 起点。这些不是证明存在真实函数入口的标记。
2. **已知原厂入口：** 单独从已验证的 Cortex-M Reset 向量入口和 V1/V2 共用的 ROM 帮助函数前导开始静态遍历；与候选根的结果隔离，避免把原厂真实入口与未证实的潜在指令地址混淆。

分析器追踪条件跳转两侧、无条件跳转、寄存器常量 `MOVW/MOVT`、字面加载、立即数加减法、同函数内确定的 SRAM 和栈写入/重新读取。汇合节点采用**只保留两条路径相同且已知的值位**的抽象解释；发现不一致时不能把其中一个常量当成必然值。遇未知存储可能覆盖 SRAM 时使局部记忆失效，遇 `BL/BLX` 时按 AAPCS 清除调用者保存寄存器及被调用者可能改写的内存状态。

对于 `BLX Rn`，只有寄存器被解析为完整常量时才报告目标地址。由原厂 Reset 入口恢复了 `0x0800123E BLX R0` 指向 `0x080323DD`（Thumb 状态）；ROM 表项 `[0x1FFFD00C]` 的回调函数地址**仍未知**，没有把 ROM 指针当作普通固件内函数地址，也没有执行它。

### 合成测试和真实固件测试

测试中专门使用预先交叉编译的 Cortex-M3 Thumb 指令字节序列，核对：

- `MOVW` → 无条件分支 → `MOVT` → RCC `STR`：跨基本块保持正确地址
- `0x20000100` SRAM 暂存 RCC 寄存器指针 → 再加载 → RCC `STR`
- 栈局部槽暂存 RCC 指针 → 重新加载使用
- 未初始化低 16 位时，不能凭 `MOVT #0x4002` 凭空推断寄存器地址
- 经过未知 `BL` 后，之前寄存器/内存别名信息不再被当作可信常量
- 两条分支常量不同：抽象状态汇合丢失冲突的已知位
- `BLX Rn` 只记录能由局部常量证明的目标

随后对 V1、V2 原厂固件复测，固定 26/30/43/13 的对照数据、ROM 分支真实指令位置，以及启动向量间接跳转。所有结果都可以在 GitHub Actions 的 JSON 工件复算。

## 三、为什么仍不能宣称“全镜像不存在动态改频”

本轮不是路径完备的形式化验证，特别是：

- 候选入口可能出现在死代码或嵌入数据；**静态候选不等于可执行代码，也不等于真的执行过**。
- 目前只对固定 RCC 基址文字池与短间隔 MOVW/MOVT 组合建立起点。经其他运算拼接、从未跟踪的指针参数传入的地址仍可能遗漏。
- 同函数内 SRAM 路径的精确传递可以建立，但跨函数传参、通过 RAM 常量表间接引用、跨中断数据竞争、函数指针和更复杂的寄存器偏移仍未完全求解。
- 未取得 ROM 回调实现，也未取得物理 UID 与 RCC 读回；可证明的仍然只是固件的**条件性 128 MHz 请求**，不是运行实测时钟。
- 对 `IT` 条件执行、别名与循环采用保守处理；可能保留额外的候选，不能将所有扫描命中列为固件必经路径。

因此，当前工程结论应保持：**暂不为某个未经验证的 MCU 型号创建确定性的板级时钟配置，也不把 48 MHz 或 128 MHz 假设写死为所有 USART/TIM 的固定时基。**

## 四、复现

```sh
python -m pip install "capstone==5.0.6"
python -m unittest discover -s tests -v
python tools/v2_rcc_cfg_dataflow.py firmware/BF_5RH_501_v2_0_9.dat --v1 firmware/BF_5RH_501_v1_1_04.dat --json
```

生成的 `v2-rcc-cfg-dataflow.json` 包括两版的已知原厂入口间接跳转、CFG 地址写入候选、新增存储指令清单、预算耗尽清单，以及所有未覆盖的分析范围。所有工具只读取原厂更新包；不创建刷写镜像、不修改硬件。

下一阶段重点可以是将新找到的 13 个标准/早期时钟写入与**函数入口级**调用图关联，并进一步对 `MOVW/MOVT` 以外的间接加载和 RAM 全局表分析，实现“指令候选 → 函数可达路径”的更严格分类。
