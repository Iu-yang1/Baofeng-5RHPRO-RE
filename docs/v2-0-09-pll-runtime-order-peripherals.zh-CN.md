# UV-5RH Pro V2.0.09：128 MHz PLL 请求的启动调用链、USART BRR 与 TIM3 PSC 交叉验证

日期：2026-11-15。研究对象：原厂 `firmware/BF_5RH_501_v2_0_9.dat` 和 `firmware/BF_5RH_501_v1_1_04.dat`。方法：解码原厂包后针对 Thumb 指令、PC 相对文字池、直接 BL 调用与条件 CFG 静态遍历，自动回归真实镜像。本次**无 SWD/刷写/实机运行，也未读取物理时钟、实际 UID 或串口寄存器**。

## 结论

**原厂固件在 Reset → ARM scatterload → 应用主入口这条静态路径上，确实安排了先进行条件性 AIR32 风格 PLL ×16 配置，再初始化 TIM3、USART 与其他外设。** `0x080340EA` 的 PLL 调用不是孤立且永远不执行的备用函数。Reset 阶段 `0x080323DC → 0x08031BF4` 的 **48 MHz** 是**早期启动的软件配置假设**，不应自动当作应用 USART 与 TIM 的最终时钟。

对真实运行频率仍有限制：ROM `SysFreq_Set` 根据 UID[31:24] 的 `0x1A/1B/1C` 分支调用，必须 ROM 操作成功、PLL 锁定并完成切换。原厂码没有在这里提供物理钟频/寄存器读回。因此下文的 128 MHz、USART BRR 和 TIM PSC 是**条件预测**，不是已测量结果。

## 1. 首次验证从 Reset 到应用主入口的完整控制流

原厂固件 V2 有如下指令与文字池证据（均由 `tools/v2_pll_runtime_order.py` 校验）：

| 执行层 | PC | 原厂实际内容 |
| --- | --- | --- |
| Cortex-M 向量 | `0x08001004` | Reset 向量 `0x0800123D` |
| Reset | `0x0800123C–0x08001242` | `LDR 0x080323DD; BLX`，随后 `BX 0x08001221` |
| 初始化阶段一 | `0x080323DC` | CRM 复位、启动前配置，调用 `0x08031BF4`（早期 PLL ×6 的软件解释） |
| 初始化阶段二 | `0x08001220–0x0800122A` | 设定 SP，`BL 0x08001EA4` 做 scatterload，然后 `BX` |
| 应用入口文字池 | `0x0800122C` | `0x080340E1`，带 Thumb 位的主入口 |
| 应用入口 | `0x080340E0` | `BL 0x080309BC` 后，`0x080340EA BL 0x080173DC` |
| PLL 包装 | `0x080173DC` | `BL 0x0803235E` → `BL 0x080194B4` → 尾跳 `0x080193E8` |
| PLL 配置 | `0x0803235E` | `0x08032386 BL 0x08001260`，参数为 `(0x10000,0x380000,1)` |
| ROM 回调 | `0x08001260` | 根据 UID 低字节字段分支访问 `[0x1FFFD000+0x0C]`，使用三级解锁/QSPI 特殊接口 |

**关键时序：** `0x080340E0` 主入口在 `0x080340EA` 前没有设备状态、波段、工作模式或固件版本条件跳转；该调用是静态主入口的直接 BL。若 HSE 启动准备就绪且 ROM 操作正常返回，才会继续后面的初始化函数。原厂轮询外部晶振就绪、PLL 就绪等循环可能等待，故“无条件调用”不是“无条件成功”。

## 2. V1.1.04 的相同结构，排除 V2 特有模式的解释

V1 的复位向量仍为 `0x0800123D`，但 `0x0800122C` 的主入口指针是 **`0x08027BE9`**，即函数 `0x08027BE8`。对应次序：

```text
V1 0x0800123C Reset
  → V1 CRM 初始化 0x080262A8
  → V1 ARM scatterload 0x08001220
  → [0x0800122C] = 0x08027BE9
  → 0x08027BE8 应用主入口
       0x08027BEE BL 0x08024978
       0x08027BF2 BL 0x080111F0
           0x080111F2 BL 0x0802622A
               0x0802624A R2=1
               0x0802624C R1=0x380000
               0x08026252 BL 0x08001260
           0x080111F6 BL 0x08013170
           0x080111FE B.W 0x080130A0
               0x080130B4 BL 0x08024BBC (RCC_GetClocksFreq)
               0x080130DE BL 0x080263C4 (TIM3)
```

两版共同具有**主入口启动 → PLL ×16 请求 → TIM3 初始化**这条相同架构，仅因应用编译布局而出现函数地址差异。此前已单独确认 ROM 辅助函数 216 字节相同。因此没有软件证据支持“V2 才加了 128 MHz”或“根据 V1/V2 菜单版号选择 PLL”的说法；但并不证明 V1 和 V2 物理芯片相同。

## 3. USART1/2/3 的嵌套调用路径

V2 应用主入口 `0x080340E0` 先做 PLL 配置，再执行连续的初始化 BL 序列。新的 CFG 深度遍历不是简单比较函数地址大小，而是逐条跟踪主函数的直接 BL、各级调用和尾跳转，找到了：

| USART | 应用主入口 → 子调用点（各段 PC） | 最终 USART_Init BL | 波特率 |
| --- | --- | --- | ---: |
| USART1 | `0x0803412C → 0x08018B8E` | `0x08018C20 → 0x08032CDC` | 115200 |
| USART2 (GNSS) | `0x080340F4 → 0x0801075E → 0x0800DA2A` | `0x08010306 → 0x08032CDC` | 9600 |
| USART3 | `0x080340F4 → 0x0801076A → 0x0800CB00` | `0x0800CA2A → 0x08032CDC` | 19200 |

上述每个节点都来自实际固件的 BL 指令或 CFG 可达路径。**但 CFG 将条件分支的两边都纳入探索**：它们是静态可能调用链，不证明每次冷启动都会执行三路 USART 初始化，尤其不能据此确定外设引脚接线和实际设备工作模式。

**USART_Init 自己会调用 `RCC_GetClocksFreq`（`0x08032D18`），不是使用早期复位阶段的固定 48 MHz 常量。** 因此当固件确实运行在后阶段 128 MHz 配置时，按复位阶段 48 MHz 算出的 BRR 不能作为实际 UART 值。

## 4. 两种条件时钟状态对应的 USART BRR 与 TIM3 PSC

依据独立验证的 AIR32 SDK `RCC_PLLMul_16 = 0x00380000`、固件 `0x10000` HSE/1、编译时 HSE 8 MHz，以及已恢复的 APB 分频表：

| 参数 | Reset 48 MHz 假设 | ROM PLL ×16 生效后 128 MHz 假设 |
| --- | ---: | ---: |
| SYSCLK / HCLK | 48 / 48 MHz | 128 / 128 MHz |
| PCLK1 (APB1 /2) | 24 MHz | 64 MHz |
| PCLK2 (APB2 /1) | 48 MHz | 128 MHz |
| TIM3 输入（APB1 定时器 ×2） | 48 MHz | 128 MHz |
| TIM3 PSC（原厂 PCLK1/1MHz−1） | 23 | 63 |
| TIM3 ARR | 1999 | 1999 |
| TIM3 更新周期 | **1 ms** | **1 ms** |

原厂 TIM3 的 `0x080193FC BL RCC_GetClocksFreq`、`0x08019408` 读取 PCLK1、`0x0801940E UDIV`、`0x08019426 BL TIM_TimeBaseInit` 实际存在；不是为了模拟而虚构的 PSC 算法。

USART 使用 STM32/AIR32 兼容的 **16 倍过采样**时，BRR 预测为：

| USART | 波特率 | Reset 48 MHz | 条件 128 MHz |
| --- | ---: | ---: | ---: |
| USART1（PCLK2） | 115200 | `0x01A1` | **`0x0457`** |
| USART2（PCLK1） | 9600 | `0x09C4` | **`0x1A0B`** |
| USART3（PCLK1） | 19200 | `0x04E2` | **`0x0D05`** |

BRR 使用 `round(PCLK/baud)` 的对应定点编码，**若 OVER8=1、外设复位态不同或实际芯片寄存器语义不同，这些数值不能直接应用**。Timer 更新周期在两种假设下都为 1 ms，故只测 TIM3 1 ms 也无法区分 CPU 主频；直接读取时钟寄存器、捕捉硬件 MCO 或借助串口时钟配置更有鉴别力。本轮未做任何这些实机操作。

## 5. 还有哪些动态状态不能由静态固件确定？

1. `0x08001260` UID[31:24] 若不在 `0x1A,0x1B,0x1C`，不会走已识别的相同 ROM `SysFreq_Set` 调用；不同分支下最终 PLL 寄存器值仍不能由代码中的 `R1` 独立推出。
2. `0x0803235E` 中的 HSE/PLL/SWS 就绪轮询只证明程序等待硬件状态，不能用软件检测结果代替晶振频率实测。
3. 本轮追踪的是 Reset 后的主初始化路径，不足以排除后续运行状态下经其他 RCC 通用函数改变分频或主频。没有证据表明按键模式或 RX/TX 必然触发频率改变，也不能简单宣称全镜像绝无此机制。
4. V1、V2 共用 SDK 时序，不意味着焊接的芯片厂商/型号必然相同；标准 AIR32F103RPT6 的 256 KiB Flash 仍和 V2 中 `0x08061A54` scatterload 读取存在矛盾。

## 6. 可复现命令与验收范围

```sh
python -m pip install "capstone==5.0.6"
python -m unittest discover -s tests -v
python tools/v2_pll_runtime_order.py firmware/BF_5RH_501_v2_0_9.dat --v1 firmware/BF_5RH_501_v1_1_04.dat --json
```

`tools/v2_pll_runtime_order.py` 输出的 JSON 包含 V1/V2 启动主指针、主初始化调用顺序、USART/TIM3 的真实 CFG 函数调用链、48/128 MHz 条件计算与未解决前提。对于无法分析的 BLX 寄存器、函数指针、ROM 本体，报告明确限制；不从“没有路径”推断“绝不执行”。测试覆盖真实原厂镜像与主入口指针、PLL BL 字节修改后的拒绝路径。

## 7. 对自主固件的意义

自主 Rust `no_std` 核心不需要因为新的 128 MHz 线索立即改变硬件目标；真正的板级 HAL 应采用时钟状态模型，USART/TIM 驱动在完成时钟切换后读取当前 PCLK（或从同一个可信 `ClockTree` 状态快照取得），再计算 BRR、PSC 和超时。若支持动态切换，则必须重新配置依赖的外设时基。当前仍未确认实际 MCU、引脚表、Flash 容量及安全恢复流程，因此**只提交研究与主机回归，不产生可刷写镜像**。
