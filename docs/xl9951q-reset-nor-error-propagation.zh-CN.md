# XL9951Q：Reset → 应用 NOR 日志恢复与擦写错误传播审计

日期：2026-11-16。基于原厂 UV-5RH Pro V1.1.04 / V2.0.09 的解码固件和已有 [恢复状态机报告](xl9951q-journal-cold-start-recovery.zh-CN.md)。**只进行离线原始 Thumb 指令、指令地址与调用图检查；没有连接、启动或刷新实体电台。**

## 一、启动可达性证据更新

| 控制流阶段 | V1.1.04 | V2.0.09 | 解释 |
| --- | --- | --- | --- |
| 原始镜像 Reset 向量 | `0x0800123D` | `0x0800123D` | Thumb 位为 1，实际执行地址 `0x0800123C` |
| Reset veneer | `0x0800123C` | `0x0800123C` | `BLX` 前置时钟初始化，再 `BX` 至 `0x08001220` |
| ARM scatterload/handoff | `0x08001220` | `0x08001220` | 初始化栈、执行 `BL` scatterload、从镜像内文字池 `BX` 进入应用 |
| 文字池中 main 指针 | `0x08027BE9` | `0x080340E1` | 和上一阶段独立 Reset 工具校验一致 |
| main 内恢复直接 `BL` | `0x08027BFC` | `0x080340F4` | main 早期主线第 4 个直呼调用 |
| 恢复函数 | `0x0800AB74` | `0x08010400` | 8 B 事务日志检查和 NOR 扇区修复，已由 PR #25 原厂指令校验 |

**更严格的新结论：** Reset / scatterload → main 的已核验跳转，加上 main 的连续早期指令和第四个 `BL`，在前置调用正常返回的前提下形成**可达的直接控制流**。已检查 main 头部在恢复前没有 `B/BEQ/BNE/CBZ/CBNZ/BLX/BX` 条件或绝对跳转，恢复调用不受本段内模式判断选择。

此为静态 CFG 和固定原始指令可达性，**不是**断言实机每次启动都必定到达；Bootloader 的进入条件、前置函数可能不返回、Reset 与散装加载异常均未被硬件验证。

## 二、NOR `0x05` 状态轮询和擦写完成含义

| 过程 | V1.1.04 | V2.0.09 | 可证事实 |
| --- | --- | --- | --- |
| NOR 状态轮询入口 | `0x080030C8` | `0x08006BD8` | 发 `0x05` RDSR，发送 `0xFF` 读字节 |
| Busy/WIP 判定 | `0x080030EA` | `0x08006BFA` | `LSLS R0,#31`：通过移位检查状态位 0 |
| Busy 回跳 | `0x080030EC` | `0x08006BFC` | WIP=1 分支返回循环开头 |
| 状态等待退出 | `0x080030EE` | `0x08006BFE` | WIP=0 时直接 POP 返回 |
| NOR 扇区擦除 | `0x08007C94` | `0x0800D334` | Write Enable / 状态轮询，再发 `0x20` 和 24 位地址，尾部跳入轮询函数 |
| NOR 页编程 | `0x08003118` | `0x08006C28` | 以 `0x100` 字节为页界限分包，发送 `0x02` 和数据，每页调用状态轮询 |
| 失败后返还给恢复函数的有效错误码 | 未确认 | 未确认 | 观察到 WIP 轮询路径没有错误码区分，恢复调用后也没有结果判断 |

**关键区别**：`0x05` 的 WIP=0 仅证明状态位表示“不忙”，不能证明操作成功或目标数据校验通过。本次检查的 NOR 状态轮询循环没有超时计数器和可见超时退出分支。这意味着若 WIP 长期保持 1，当前软件循环可能长时间停留；但真正时间和是否被看门狗复位仍需进一步证据。

恢复包装函数（V1 `0x0800ED50` / V2 `0x08014A28`）依次触发擦除和 4096 B 编程，尾部**直接**跳入 NOR 页编程。恢复调用之后紧接着元数据清理：

- V1：`0x0800AC08 BL 0x0800ED50` → `0x0800AC0C BL 0x08007C68`。
- V2：`0x08010494 BL 0x08014A28` → `0x08010498 BL 0x0800D308`。

两个 `BL` 之间均没有根据先前返回状态选择是否清除日志的指令。这是**相邻调用指令级证据**；即使某些底层操作最终返回了一个字节，它也没有被这条恢复函数调用者检查。

## 三、内部 MCU Flash 的状态反馈也不能混作 NOR 成功验证

V1 `0x08002E70`、V2 `0x08006980` 片内 Flash 擦除函数中，确实存在一个控制器状态读取/比较路径（例如 V2 `0x0800698E CMP R0,#4`、`0x08006990 BNE`），与上面 NOR 的 SPI `0x05` 完全不同。

它仅能确认**片内 Flash 擦写函数尝试根据控制器状态决定是否进入擦除步骤**；没有证据表明这个判定等价于 NOR 备份验证，也没有确认 XL9951Q 实际接受的内部 Flash 物理擦除页尺寸。

## 四、可复现的故障模式与尚未验证事项

| 触发条件 | 已定位的路径 | 可能的结果 | 当前证据级别 |
| --- | --- | --- | --- |
| NOR WIP=1 持续不变 | `0x05` 状态循环仅依赖 WIP 位清零 | 一直在轮询；是否被看门狗打断未知 | 静态循环已核对 |
| NOR 指令结束但内容与预期不同 | Restore → NOR `0x02` → RDSR WIP=0 → 日志擦除 | 已损坏目标可能保留且不能再次由该日志自动恢复 | 静态无成功校验，故障未实测 |
| 上次备份扇区 `0x001FE000` 内容已损坏 | 冷启动比较/写回流程只比较备份与目标 | 可能把损坏的备份重写到目标 | 未见独立备份 CRC，但其他可能的校验入口未全扫描 |
| MCU Flash 元数据半字写入或擦除失败 | 完成标记/清除日志路径不核对硬件全状态 | 恢复标志可能不可靠 | 需要硬件模拟、看门狗和读回确认 |
| 启动前置初始化异常或未返回 | 只能走到正常返回情况下的恢复调用 | 该次启动可能无法进入恢复函数 | 源代码静态不能证实每次复位真实执行 |

上述均不构成当前真实电台存在故障的断言。下一阶段的进一步取证应从 ROM/Bootloader 的启动条件、NOR IO 例程 `0x08031814`（V2）/ `0x080257A0`（V1）的 SPI 控制器错误反馈，以及看门狗初始化与超时状态分支入手。

## 五、脚本、回归与明确结论范围

```sh
python -m pip install "capstone==5.0.6"
python tools/xl9951q_reset_nor_error_audit.py --json
python -m unittest discover -s tests -v
```

新的审计器同时复用已通过的 Reset→main 和恢复状态机验证，并对 main 早期 BL、NOR 状态轮询、擦除/编程/尾调用、片内 Flash 状态比较及紧邻恢复日志清除进行独立指令断言；测试包含原始镜像正例和关键跳转变异负例。只归档 JSON、函数及指令地址，不产生可烧录固件，也不运行原厂升级器。

**已验证：** 正常前置调用返回情况下的 V1/V2 Reset→应用恢复静态可达性、NOR WIP 轮询和恢复后无独立结果判断。**未验证：** 真实 SPI3 事务结果、NOR 物理写入成功率、系统看门狗时序、实际断电恢复可靠性、XL9951Q 商业型号与片内 Flash 容量。
